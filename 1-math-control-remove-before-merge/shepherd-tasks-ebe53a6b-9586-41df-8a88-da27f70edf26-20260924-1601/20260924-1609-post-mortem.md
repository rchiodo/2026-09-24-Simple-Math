## Section 8: Observations and Recommendations

### 8.1 What worked well

- The recovery run resumed from durable GitHub state rather than repeating completed [Issue #2](https://github.com/rchiodo/2026-09-24-Simple-Math/issues/2) work.
- Campaign metadata, base branch, task dependency, issue linkage, and exact PR head were revalidated before progression.
- CCRA's earlier finding led to a focused positional-invocation regression test; the fresh review confirmed convergence with zero findings.
- Local acceptance and CI were both bound to the corrected head. All 17 local tests and both substantive checks passed.
- Fail-closed gates prevented command-construction defects from becoming success-shaped results.
- Stage 40 verified the merge and issue closure persistently.

### 8.2 What could be improved

- The final atomic gate was assembled as a long inline PowerShell command and required four executions because of argument-binding and type-comparison defects.
- The current run manifest listed both campaign tasks even though only one task produced session artifacts. This is correct campaign scope but makes current-run throughput ambiguous without predecessor context.
- Token-type labels remained redacted, requiring input/output classification by magnitude.
- `assistant.idle` appeared once at normal completion in each JSONL session, so idle events alone cannot be treated as timeout evidence.

### 8.3 Recommendations

1. Move the atomic readiness gate into a versioned, testable script with typed parameters and unit coverage for native argument forwarding, GraphQL numeric values, and comma-separated `gh --json` fields.
2. Emit a compact per-task stage outcome JSON containing issue, PR, exact head, phase duration, review ID, findings, test count, CI state, and semantic result.
3. Distinguish `targetTasks`, `processedTasks`, and `precompletedTasks` in the stage-25 run manifest.
4. Record an explicit idle reason or timeout marker rather than requiring post-mortem logic to infer whether `assistant.idle` is normal.
5. Preserve the single-writer readiness model demonstrated by the successful recovery: stage 30 validates and stops while draft; stage 40 alone marks ready.
6. Keep additive PowerShell CLI changes covered by both named and positional invocation tests.

### 8.4 Control-treatment interpretation

Lesson propagation remained `off`, and `campaign-lessons.md` stayed unchanged. The recovery therefore measures orchestration behavior without cross-task lesson injection. The task still benefited from direct review feedback retained in [PR #5](https://github.com/rchiodo/2026-09-24-Simple-Math/pull/5), which is task-local remediation rather than campaign lesson propagation.
